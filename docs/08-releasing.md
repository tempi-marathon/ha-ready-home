# Releasing (maintainers)

Releases are **immutable**: once a release is published it cannot gain or change assets, and
its tag name is reserved forever, even if the release is deleted. The release workflow is built
around that: it checks everything first, then creates a draft, attaches `ready_home.zip`,
publishes, and verifies.

## Tag names

- Stable: `vX.Y.Z` (for example `v0.3.0`)
- Beta: `vX.Y.Z-beta.N` (for example `v0.3.0-beta.4`); release candidate: `vX.Y.Z-rc.N`
- `N` starts at 1 with no leading zeros. Anything else is rejected.
- **Never reuse a tag.** If a release is wrong, ship the next number. History: `v0.2.0` was
  published before its zip was attached, so it is unusable and its name is burned (its git tag
  still points at `5d17b86`); `v0.2.1` is its replacement.

## Versions in the repository

`manifest.json`, `pyproject.toml` and `package.json` (and `package-lock.json`) carry the same
version. Before the first beta of a new line, bump them in a PR to the base `X.Y.Z` (for the
`v0.3.0-beta.N` line: `0.3.0`). Betas do not need their own bump: the build stamps the full tag
version (`0.3.0-beta.4`) into the zip's `manifest.json` only, and changes nothing else in that
file. A stable release ships exactly what is committed. The workflow refuses to release if the
three files disagree or do not match the tag's base version.

## Cut a release

Always ship a **commit SHA**, never a moving branch.

```bash
git fetch origin
SHA=$(git rev-parse origin/main)    # use origin/main, local main can be stale

# 1. Rehearse: builds and verifies the zip, uploads it as a workflow artifact,
#    creates no tag or release. dry_run is on by default.
gh workflow run release.yaml -f tag=v0.3.0-beta.4 -f ref=$SHA

# 2. Publish for real, with the same SHA.
gh workflow run release.yaml -f tag=v0.3.0-beta.4 -f ref=$SHA -f dry_run=false
```

The workflow fails before anything permanent happens if the tag is malformed or already used
(as a git tag or a release), if the ref does not resolve, if the commit has no successful `Test`
and `Validate` run, or if the zip's manifest is wrong. Betas and release candidates are
published as pre-releases; only stable tags are marked Latest.

**Do not create or publish a release by hand** before the zip is attached. That is how
`v0.2.0` was burned. If a run fails before publishing it removes its draft, so you can retry
the same tag. If it fails after publishing, the release is immutable: check it with
`gh release verify <tag>` and use the next tag if it is bad.

## Release notes

Notes are generated by GitHub and grouped by PR label (`enhancement`, `bug`, `accessibility`,
`documentation`, everything else). PRs labelled `internal` or `dependencies`, and Dependabot
PRs, are left out. Label tooling-only PRs (Spec Kit scaffolding, CI chores) `internal`.

The notes start from the previous tag, chosen automatically:

- a beta or rc starts from the previous beta/rc of the same `X.Y.Z` line, or from the last
  stable release for `beta.1`;
- a stable release starts from the previous stable release.

Override with `-f notes_from=<tag>`.

## Promote a beta to stable

Build the stable tag from the **same commit** the last good beta shipped, in one pass:

```bash
SHA=$(git rev-parse v0.3.0-beta.4^{commit})
gh workflow run release.yaml -f tag=v0.3.0 -f ref=$SHA                   # dry run
gh workflow run release.yaml -f tag=v0.3.0 -f ref=$SHA -f dry_run=false
```

Never publish `v0.3.0` by hand and attach the zip afterwards. Because the committed versions
already equal `0.3.0`, the stable zip's `manifest.json` is exactly the committed file.
